定位：在 X-AnyLabeling 原工程、原画布、原数据格式和原训练模块上增加功能。

## 1. 项目方向

源码仓库：[CVHub520/X-AnyLabeling](https://github.com/CVHub520/X-AnyLabeling)。

在上游仓库的基础上建立二次开发分支，沿用原软件的界面框架、图片画布、图形编辑、标注保存、模型加载、训练与导出流程。新增功能直接进入原程序的菜单、工具栏和停靠面板，不再维护另一套独立标注器。

本项目需要补齐的核心体验是：

**导入图片 → 可视化定义类别和骨点 → 顺序点击标注 → 选择 CPU/GPU 训练 → 使用训练结果批量预标注 → 人工微调确认 → 再训练。**

用户应能完成上述流程而无需手写 YAML、输入 Python 路径、手动拼接模型配置或查找训练输出目录。高级入口仍保留，满足用户自行填写参数的需求。

### 2.2 需要优先修正的数据行为

读取当前 `general.py` 可见：未启用审核过滤时，缺失标注文件可能被当作背景数据；训练/验证划分使用随机抽样。对本项目的半自动标注流程，需要增加更严格的默认准入和固定划分，避免把“还没标”当作“没有目标”，也避免每轮更换验证集。

这属于本项目的改造依据，不代表已复现用户本地版本的错误。参见 [工作区数据准备源码](https://github.com/CVHub520/X-AnyLabeling/blob/main/anylabeling/services/auto_training/ultralytics/general.py)。

## 3. 原界面怎么改：保留标注工作区，增加流程入口

### 3.1 主界面布局

```text
原菜单与工具栏 + 新增：项目向导 / 骨架模板 / 训练 / 自动标注与审核
┌──────────────────────────────────────────────────────────────┐
│ 项目进度：导入 → 定义标签 → 人工标注 → 训练 → 自动标注 → 审核 │
├────────────┬────────────────────────────┬────────────────────┤
│ 原图片列表 │ 原标注画布                 │ 原标签/实例列表    │
│ + 状态筛选 │ + 骨架线、当前骨点提示     │ + 当前模板         │
│ + 审核进度 │ + AI候选叠加               │ + 顺序骨点列表     │
├────────────┴────────────────────────────┴────────────────────┤
│ 当前操作说明 / 保存状态 / 接受候选 / 审核通过并下一张         │
└──────────────────────────────────────────────────────────────┘
```

新增内容使用原有 Qt 菜单、对话框、停靠面板和主题样式。新手模式收起不相关的高级入口，熟练用户可展开原工具；原有标注功能需要回归验证。

### 3.2 新手只需完成的操作

1. 点“新建项目”，选图片文件夹及“检测”或“姿态”。
2. 添加类别；姿态项目点“创建骨架模板”。
3. 完成引导标注；软件显示已审核图片数及数据不足提示。
4. 点“训练”，选推荐模型及设备，必要时修改参数。
5. 训练结束点“用此模型自动标注”，先看小批预览。
6. 点“开始批量标注”，随后在原画布上审核和微调。

每一步都显示“下一步”和简短说明。所有失败提示提供具体处理动作，例如“未找到训练运行环境 → 准备应用专用环境”。

## 4. 自定义骨点：本项目的主要标注扩展

### 4.1 图形化骨架模板编辑器

用户可以在原程序中创建模板，设置：

- 模板名称和适用类别。
- 骨点数量、中文显示名、稳定 ID、标注顺序和颜色。
- 哪两个骨点需要连线。
- 左右对称骨点配对。
- 示意图与简短标注说明。

提供列表编辑、拖动排序和示意图点选两种方式。支持保存、复制及导入导出模板。比如“机械臂五点”：底座、肩、肘、腕、夹爪；不限制为人体或固定骨点数量。

首版每个姿态项目使用一套统一骨点定义。多个类别需要不同数量或不同语义骨点时，向导建议分开建项目；不直接承诺所有 YOLO 后端都支持混合骨架。

### 4.2 顺序点选与自动分组

具体交互：**画框 → 点击“开始骨点” → 按提示连续点选 → 拖动修正 → 完成实例。**

- 建立目标框时自动分配当前图内唯一的实例分组。
- 所有骨点自动归入当前实例，无需用户逐个填写分组编号。
- 右侧突出显示“当前：左肘，下一步：左腕”。
- 点完一个骨点自动进入下一个；已定义的连线即时显示。
- 支持可见、遮挡但可判断位置、位置未知三种状态。
- 未知点可以跳过，仍保留模板中的位置，不能打乱后续骨点索引。
- 可撤销、返回上一个骨点、复制实例布局、整体移动以及单点拖动。
- 骨架线作为辅助显示，不以普通线段标签重复写入训练数据。

复制上一张图的骨架属于辅助结果，仍需当前图人工确认。目标框允许人工修改，不强制用骨点范围替代完整目标范围。

### 4.3 数据兼容与模板版本

继续使用上游的框、点和分组方式表达正式标注，显示名与稳定骨点 ID 的映射保存在项目模板中。新增元数据优先放在兼容扩展字段或独立侧车文件中；以旧格式读写回归测试确认，不预设所有未知字段都能被任意历史版本保留。

模板变更规则：

| 修改 | 行为 |
| --- | --- |
| 改颜色、显示名 | 保持语义 ID，并更新显示映射 |
| 增删骨点、重排训练顺序 | 生成新版本，预览并确认标注迁移 |
| 修改骨点语义 | 视为不兼容变更，不能只重命名旧数据 |
| 使用旧模型 | 校验模板版本、骨点数和语义映射，不一致时阻止直接应用 |

由模板自动生成上游所需的 Pose Config，以及相应训练数据配置。左右映射未定义时默认关闭水平翻转，未知点、遮挡点的导出转换必须通过测试。采用三维骨点格式时，目标映射为未知 `v=0`、有定位的遮挡 `v=1`、可见 `v=2`。

## 5. 训练扩展：增强现有训练窗口

### 5.1 不重复开发训练引擎

以已有 `UltralyticsDialog` 和 `services/auto_training/ultralytics/` 为扩展位置，沿用数据、配置、训练和结果显示流程。在其上增加项目模板绑定与面向新手的入口。

当前界面已连接环境管理、训练管理、导出管理和校验模块，适合在这些边界处扩展，避免继续向主标注窗口堆放业务逻辑。参见 [训练窗口源码](https://github.com/CVHub520/X-AnyLabeling/blob/main/anylabeling/views/training/ultralytics_dialog.py)。

### 5.2 用户能填写的参数

| 分组 | 新手默认显示 | 专业模式扩展 |
| --- | --- | --- |
| 模型 | 家族、规模、初始权重 | 本地结构配置、经验证的自定义权重 |
| 设备 | 自动推荐、CPU、指定 GPU | 后续验证多卡后再开放 |
| 训练 | 轮数、图片尺寸、批大小、学习率 | 优化器、权重衰减、预热、调度等 |
| 数据 | 已审核数量、固定划分、类别统计 | 来源分组、单独测试集、数据快照 |
| 增强 | 推荐配置 | 当前模型支持的几何/颜色增强及姿态相关参数 |
| 输出 | 保存位置、运行名称 | 检查点策略、恢复与导出选项 |

所有参数有中文说明、范围检查和恢复推荐配置。保存训练配方，运行前展示实际生效值。不同模型不支持的选项应隐藏或解释禁用原因，未知参数不能静默丢弃。

第一轮提供短试跑以验证数据和环境，再正式训练；不承诺固定轮数或少量数据必然达到理想精度。

### 5.3 CPU/GPU 与环境准备

保留上游的外部训练 Python 选择作为专业入口；新增应用专用运行环境向导，默认不要求新手查找解释器。

检测分为两层：**训练环境中的 PyTorch 设备可用性**与**标注推理环境可用性**。原 EXE 文件名中的 CPU 不能直接决定新训练后端是否可用 GPU，两者需分别验证。

- CPU 是必备路径，推荐小模型并说明训练可能较慢。
- 首版 GPU 训练以经实测的 NVIDIA CUDA 单卡为目标。
- AMD/Intel 等设备按适配后端实测开放，不承诺通用支持。
- 用户选择 GPU 失败时明确报告，不静默切为 CPU 长时间运行。
- 运行环境安装在应用专用目录，沿用或修改上游环境逻辑时必须检查自动安装目标，避免改动用户其他项目。
- 运行环境与模型包准备好后支持离线使用。

上游当前项目声明 Python >=3.11 并使用 PyQt6；开发时以锁定提交确定依赖，分别验证桌面端和训练端。[依赖配置依据](https://github.com/CVHub520/X-AnyLabeling/blob/main/pyproject.toml)

### 5.4 多 YOLO 家族策略

| 家族 | 本项目优先适配 | 发布条件 |
| --- | --- | --- |
| YOLOv8 | 检测、姿态 | 短训练、权重回载、预标注与模板语义校验通过 |
| YOLO11 | 检测、姿态 | 同上，首版必测 |
| YOLO26 | 检测、姿态 | 固定训练后端版本后作为扩展目标验证 |
| YOLOv5 与其他家族 | 按实际后端能力安排 | 需要时提供独立适配器，不凭文件后缀判断兼容 |

沿用上游已有模型管理体系，增加项目级能力清单。上游可推理的模型数量不能直接作为本项目可训练的兼容数量。ONNX 通常用于推理，不能当作继续训练的检查点；同为 PT 格式也不代表结构兼容。

## 6. 自动预标注与人工微调：沿用模型应用链路，增加审核层

### 6.1 模型如何回到标注界面

首版优先沿用上游的 **训练完成 → 导出 ONNX → Apply 注册并加载到自动标注面板** 路线，将必要步骤整合为一个向导。检查导出的类别与骨点顺序、运行环境及模板信息，再运行小批预览。

导出失败时显示原因和可用处理方式，不能把“训练完成”误报为“自动标注已可用”。后续如增加直接使用 PT 推理，也应接入原模型管理接口并独立测试。[现有模型导出实现](https://github.com/CVHub520/X-AnyLabeling/blob/main/anylabeling/services/auto_training/ultralytics/exporter.py)

### 6.2 批量标注默认行为

1. 默认处理尚未审核的图片。
2. 若用户选择全量推理，已有人工标注保留，AI 结果作为对照候选。
3. 批量候选存入独立目录，记录模型、模板、阈值、图片及任务版本。
4. 原画布叠加显示候选，用户可以接受、删除、补标、拖动微调。
5. 只有“审核通过”才提交正式标注；推理结束不自动改变审核状态。
6. 提交时检查人工标注版本，发生冲突先合并处理，不能覆盖任务运行期间的修改。
7. 支持取消、按图片恢复及撤销本轮未接受候选。

批量任务执行中必须拦截原先可能直接写入工作区的路径，先写候选存储；复用原推理能力不等于可以直接沿用其提交方式。

### 6.3 复用 `checked`，补充审核规则

- `checked=true` 作为人工审核完成的基础信号，不再新建一个互相矛盾的正式审核标记。
- 对已审核标注的实质修改，自动置为待审核。
- 未标注、AI 待审核、人工编辑中、已审核、已排除等工作流状态以侧车记录表示，并与 `checked` 明确映射。
- 明确确认无目标的图片，写入已审核空标注，才能作为默认负样本。
- 同图既有人工又有 AI 内容时，整图审核完成前不得进入默认训练输入。
- 单独的训练/验证/测试归属不因审核通过而改变。

审核队列优先显示低置信度、空预测、缺点和异常骨架，同时抽查高置信度样本。模型可能自信地漏检，因此不能只审核低分结果。

## 7. 项目数据和训练数据扩展

### 7.1 保持上游标注文件为主要依据

```text
project/
  project.json             # 类别、路径、当前骨点模板和项目配置
  images/                  # 托管图片或导入清单
  annotations/             # 上游兼容 JSON，使用原输出目录设置
  .xal_workflow/           # 本项目新增的辅助数据
    templates/             # 骨点模板及版本
    proposals/             # 按任务隔离的 AI 候选
    reviews/               # 来源、工作流和冲突检测记录
    splits/                # 固定 train/val/test 清单
    manifests/             # 图片哈希、标注哈希、数据版本
    backups/               # 标注与模板恢复信息
  runs/                    # 沿用训练输出与导出结果
```

具体输出目录通过上游设置适配。首版使用少量 JSON/JSONL 文件，避免为普通本地项目强制引入数据库；后续大规模索引确有需要时再增加可重建缓存。

### 7.2 数据集生成必须补充的规则

- 默认只使用已审核且通过校验的数据；缺失 JSON 不能自动算负样本。
- 固定划分清单、随机种子及版本，每次训练复用，新增审核数据默认只加入训练集。
- 同视频、同采集组按来源分组，完全重复图片不能跨集合。
- 数据校验发现骨点顺序、类别映射、坐标或实例关联错误时阻止启动并定位到图片。
- 每轮训练保存标注内容快照、模板版本、划分和有效参数。
- 上游的图片链接/复制机制需要进一步约束：对引用图片记录内容哈希，变更时阻止复用旧快照；需要真正冻结内容时复制图片。只建立符号链接并不能保证图片不可变。
- 用户提供的外部现成数据集也要经过划分、标签结构与模板校验，不能绕过全部检查。

### 7.3 Windows 与 Ubuntu 项目迁移

使用相对路径；项目外图片可通过向导打包或重新定位。迁移后重新检测本机训练设备和解释器，不搬用 Windows 的盘符及 Python 路径。两平台不要求训练结果逐位一致，但类别、骨点语义、审核状态和图片分组必须一致。

新增业务模块通过 Qt 信号或小型接口与原窗口交互，尽量减少原大文件中的新增代码。不要通过大段复制原标注窗口或另造训练引擎实现扩展。

关键连接关系：

```text
项目向导 → 项目配置 + 骨点模板
骨点模板 → 原画布的连续点选控制 → 原 Shape/LabelFile
已审核标注 + 固定划分 → 原数据转换/训练模块
训练结果 + 模板元数据 → 原导出/模型加载模块
原推理结果 → 候选存储 → 原画布审核 → 正式标注
```
