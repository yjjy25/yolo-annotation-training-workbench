# 发行构建说明

源码包含 Electron UI、完整 X-AnyLabeling 扩展、启动器及构建脚本；不包含用户项目、测试数据、模型训练结果或数 GB 依赖缓存。版本与依赖锁定见 `desktop/package.json` 和 `文档/*依赖锁定.txt`。

上游源码：https://github.com/CVHub520/X-AnyLabeling ，基线 `745f6c355f94cddb06f6965b3a4118f82033e935`。扩展基于该目录源码运行，不需要原 Windows 单文件 EXE。保留上游 GPL3 和第三方许可；Ultralytics 及权重另遵循其提供方许可。

## 准备依赖

- Windows 构建环境使用 Python 3.12.10 便携发行版，将解释器放在 `.runtime/python`，依赖放在 `.venv/Lib/site-packages`。`python312._pth` 内容参考源码中的同名文件。安装项目依赖、Torch 2.10.0+cu128、torchvision 0.25.0、Ultralytics 8.4.178、polars 1.35.2；完整锁定清单随源码提供。不要使用系统 Python 3.14 替代。
- 执行 `npm --prefix desktop ci`，下载并准备 Electron 44.8.0。
- 把选定权重放入 `.runtime/pretrained`，本版使用 yolov8n.pt、yolov8n-seg.pt、yolov8n-pose.pt、yolo11n.pt。权重来源为 Ultralytics 官方发布。
- 本版字体为 Google Fonts Noto Sans SC：`.runtime/fonts/NotoSansSC.ttf`；许可在同目录 `OFL.txt`。源包包含字体，便于重现中文界面。
- Ubuntu 源码运行可参考 `setup-linux.sh` 和 `start.sh`，会在项目内新建独立环境并联网下载依赖。正式自带环境的 DEB 使用以下发行脚本。

## Windows

使用项目便携 Python 执行：

```powershell
.runtime/python/python.exe .packaging/build_release.py stage windows
.runtime/python/python.exe .packaging/build_release.py windows-exe
```

需系统自带 .NET Framework 4 编译器。安装器以 ZIP64 作为离线载荷，附加长度与 `XALPACK1` 标记。`windows-sfx` 子命令只用已有 ZIP 重建安装器；`update_windows_payload.py` 只替换指定小文件，初次完整构建仍须执行 `windows-exe`。

## Ubuntu amd64

在 Linux/WSL 环境准备官方 Electron Linux x64 ZIP 至 `.packaging/downloads/electron-linux.zip`；uv 官方 Linux tar.gz 至 `.packaging/downloads/uv-linux.tar.gz`。

```bash
bash .packaging/prepare-linux.sh
.packaging/linux-python/bin/python3 .packaging/build_release.py stage linux
.packaging/linux-python/bin/python3 .packaging/linux_manifest.py
```

`prepare-linux.sh` 使用项目内 uv/standalone Python 和缓存，不向系统 Python 安装库。阶段目录中的 Python 及模型需要与 Windows 分开准备。

本版最终 DEB 在 Windows 端读取 Linux 阶段文件和符号链接清单构建，避免 WSL/NTFS 大量小文件重复访问。安装 zstandard 0.25.0 到 `.packaging/python-build-modules` 后执行：

```powershell
.runtime/python/python.exe .packaging/build_deb.py
```

DEB 使用 zstd 数据归档；Ubuntu 22.04+ 的 dpkg 支持此格式。构建无需 root，安装到系统 `/opt` 时仍需 apt 的正常安装权限。

## 验证

`desktop/package-qa.cjs` 只有在明确设置 `XAL_ELECTRON_QA=1` 和 `XAL_PACKAGE_TEST=1` 时运行。`XAL_PACKAGE_TEST_ROOT` 须为独立绝对路径，脚本会在其中生成6张合成图及独立检测/姿态项目；设备通过 `XAL_PACKAGE_DEVICE=cpu` 或 `0` 指定。

验证程序截图、拖动坐标、多个类别、实例分组、实际训练及批量候选，并检查人工标签哈希不变。测试结束退出自有进程。不要把合成验收数据当作真实训练效果评测。

## 0.4.1 发布步骤与源码整理

版本统一读取 `desktop/package.json`。Installer.cs 的 @VERSION@ 由构建脚本替换，不要直接手工编译模板。使用新的版本目录进行完整 staging，避免增量刷新遗漏文件；旧 refresh_sources.py 仅为历史工具，不用于 0.4.1 正式发布。

Linux stage 完成后，在 WSL/Linux 执行 `.packaging/linux-python/bin/python3 .packaging/linux_manifest.py`，保存符号链接、文件和目录清单。然后在 Windows 用项目 Python 执行 `build_deb.py`。Windows 执行 `build_release.py windows-exe`。两者使用 `.partial` 文件完成后替换成品。

执行 `.runtime/python/python.exe .packaging/verify_release.py`：读取 EXE ZIP64、测试全部 ZIP CRC、流式读取 DEB、校验全部应用源码与当前源码一致，检查 Linux 沙箱权限与程序数据排除，输出 SHA256 与对应版本的 release-<版本>.json。

执行 `.runtime/python/python.exe .packaging/package_source.py`：生成可作为新 GitHub 仓库根目录的干净源码文件夹及 ZIP，附逐文件 SHA256 清单；不携带嵌套 .git、用户项目、开发环境和模型权重。源码开发可用根目录 setup-windows.ps1 / setup-linux.sh；构建离线发行包仍需前述完整运行库准备。

执行 `.runtime/python/python.exe .packaging/split_release.py`：生成每片不超过 2000 MiB 的 GitHub Releases 分卷、SHA256 清单和 join.py。完整 EXE/DEB 本身保持可直接安装；仅上传分卷时须同时提供重组脚本和清单。

Qt 测试请使用一个会话级 QApplication，参数单元测试应模拟进程启动；真正训练由独立 package-qa.cjs 验证，避免测试替身异步回调导致 Qt 在退出时中断。


0.5.1：分卷输出在 `发行包/GitHub-Releases/<版本>/`，避免不同版本的 parts.json 混用。模型导出依赖包含 ONNX 与 ONNX Runtime；可用 `XAL_QA_MODELEXPORT=1` 和独立 `XAL_QA_MODELEXPORT_ROOT` 在包内验收转换流程。

## 发行包保留规则（2026-10-20 起）

用户要求只保留最新一个已验证正式版本。每次发布结束后，按 `文档/发行包保留与清理规则.md` 整理旧安装包、旧分卷及不再使用的打包副本；新版本校验或发布未完成时保留上一版。旧源码及历史 Git 先归档，运行环境和用户项目保留。此规则没有后台定时清理任务。
